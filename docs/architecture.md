# Как устроен Pip: объяснение для защиты

Pip — клиентское приложение на Flutter для существующего сайта `pip.kz`. Оно показывает услуги, портфолио, статьи и контакты, а также позволяет заполнить заявку. Данные берутся из того же серверного источника, что и на сайте. В приложении нет отдельной базы с копиями проектов и собственного административного кабинета.

## Основные понятия на примере этого проекта

| Понятие | Что это означает здесь |
| --- | --- |
| Flutter | Набор средств для построения интерфейса из виджетов. Исходный код используется для Android, iOS и Web; сборка и проверка каждой платформы всё равно нужны отдельно. |
| Dart | Язык, на котором написаны экраны, модели, сетевые запросы и тесты приложения. |
| Виджет | Описание части интерфейса: текст, кнопка, карточка, экран. Flutter собирает из них дерево и обновляет его при изменении состояния. |
| Клиент | Это приложение: получает данные, отображает их, проверяет форму и отправляет запросы. |
| Сервер | Существующий сервис `pip.kz`: обрабатывает запросы, применяет правила доступа и проверки, читает или сохраняет данные CMS. |
| API | Согласованные маршруты и форматы обмена между приложением и сервером. Например, `GET /projects` означает запрос списка проектов. |
| JSON | Текстовый формат обмена: объекты, массивы, строки, числа и другие простые значения. Изображение передаётся ссылкой, после чего загружается отдельным запросом. |
| HTTPS | Защищённое соединение, через которое клиент обращается к рабочему API. |
| CMS | Уже существующая система управления контентом студии. Там редактируются материалы и принимаются заявки; клиент не подключается напрямую к её базе данных. |

Приложение строит собственные Flutter-экраны из данных JSON. Оно не загружает страницы сайта целиком в WebView.

## Три слоя клиентского приложения

```text
1. Интерфейс
   lib/app + lib/features + lib/shared
   Экраны, навигация, ввод, загрузка, ошибки
                       ↕ модели и Future
2. Данные
   StudioRepository → ApiStudioRepository
   Операции приложения, маршруты, преобразование JSON в модели
                       ↕ ApiResponse / ApiException
3. Сетевой транспорт
   ApiClient + ApiConfig
   HTTPS, заголовки, JSON, таймаут, HTTP-статусы
                       ↕ HTTPS + JSON
   Существующее API https://pip.kz/api/v1
                       ↕
   CMS студии
```

Экрану не нужно знать, как склеивается URL или разбирается HTTP-ошибка. Он вызывает, например, `repository.projects(...)` и получает `ContentPage<StudioProject>`. `ApiStudioRepository` знает маршрут и поля ответа. `ApiClient` умеет отправлять JSON-запросы, но не знает, как нарисовать карточку проекта.

`StudioRepository` — интерфейс, то есть договор о доступных операциях. `ApiStudioRepository` выполняет его через сеть, а `DemoStudioRepository` возвращает локальные примеры. В тесте можно передать ещё одну реализацию с заранее известным ответом. Передача репозитория в `PipApp` через конструктор называется внедрением зависимости: объект получает нужный инструмент извне и не создаёт жёстко заданный источник данных внутри себя.

Слово «репозиторий» здесь обозначает слой работы с данными. Оно не означает, что этот класс сам содержит базу данных, и отличается от Git-репозитория с исходниками.

## Что происходит при открытии портфолио

1. Пользователь выбирает вкладку «Портфолио». `StudioShell` меняет выбранный индекс и показывает `PortfolioScreen`. Экраны хранятся в `IndexedStack`, поэтому уже созданная вкладка сохраняет своё состояние при переключении.
2. Экран получает `Future` из `repository.projects(ContentLocale.ru, ...)`. Начальная загрузка запускается при создании состояния экрана, а не заново при каждом вызове `build`.
3. `ApiStudioRepository` формирует маршрут `projects` и параметры `lang`, `page`, `limit`, при поиске — `q`.
4. `ApiClient` добавляет базовый адрес, выполняет HTTPS GET и ожидает ответ.
5. Сервер читает опубликованные записи из CMS и возвращает JSON.
6. Транспорт разбирает ответ, статус и метаданные. Репозиторий проверяет поля и создаёт объекты `StudioProject`.
7. `FutureBuilder` внутри `AsyncContent` получает результат: показывает карточки, пустое состояние или ошибку с повтором.
8. Нажатие на карточку открывает экран деталей. Он отдельно запрашивает `GET /projects/{slug}`: в списке нет полного текста и галереи.

`IndexedStack` создаёт набор вкладок заранее, поэтому часть начальных запросов может начаться ещё до нажатия на конкретную вкладку. Это допустимая особенность текущей реализации, а не загрузка исключительно по первому нажатию.

Пример запроса списка:

```http
GET /api/v1/projects?lang=ru&page=1&limit=20&q=%D1%81%D0%B0%D0%B9%D1%82 HTTP/1.1
Host: pip.kz
Accept: application/json
```

Здесь `q` содержит слово «сайт», закодированное для URL. Такое кодирование выполняет библиотека `Uri`. Упрощённый пример ответа:

```json
{
  "data": [
    {
      "id": 123,
      "slug": "example-site",
      "title": "Пример проекта",
      "excerpt": "Краткое описание",
      "category": "Сайт"
    }
  ],
  "meta": {
    "lang": "ru",
    "pagination": {
      "page": 1,
      "limit": 20,
      "total": 21,
      "totalPages": 2,
      "hasNext": true,
      "hasPrevious": false
    }
  }
}
```

Это учебный фрагмент формата, а не запись из production. В полном ответе есть и другие поля. `data` — сами данные, `meta` — сведения об ответе. DTO называют формат данных, передаваемый по сети. В этом проекте адаптер вручную преобразует поля JSON в типизированные модели; отдельная генерация клиента из OpenAPI не используется.

## Состояние и асинхронность

`StatelessWidget` описывает интерфейс через входные значения и не хранит собственного изменяемого `State`. Например, `PipApp` получает репозиторий и настраивает `MaterialApp`. Такой виджет тоже может перестраиваться, если родитель передаст новые значения.

`StatefulWidget` связан с объектом `State`, который хранит изменяемые данные. У `PortfolioScreen` это текст поиска, текущая загрузка и дополнительные страницы. У `BriefScreen` — контроллеры полей, выбранные услуги, ошибка, признак отправки и ключ заявки.

`setState` сообщает Flutter, что состояние изменилось и интерфейс нужно перестроить. Он не сохраняет данные в CMS. `mounted` проверяется после ожидания, чтобы не обновлять экран, который пользователь уже закрыл. Контроллеры и таймеры освобождаются в `dispose`.

`Future<T>` — результат типа `T`, который появится позже или завершится ошибкой. `async/await` позволяет дождаться сети, не блокируя обработку интерфейса. Само слово `async` не создаёт отдельный поток. `FutureBuilder` связывает результат `Future` с состояниями «загрузка», «данные» и «ошибка».

## Поиск, страницы и запоздалые ответы

Проекты загружаются страницами по 20 элементов. Кнопка «Загрузить ещё» появляется, если сервер сообщает `hasNext: true`. Репозиторий хранит номер следующей страницы в строковом `nextCursor`, а при запросе преобразует его в API-параметр `page`. Уже известные ID помогают не добавлять дубли карточек.

Новый поиск сбрасывает страницы. Запрос отправляется после паузы ввода в 300 мс, чтобы не делать отдельный запрос на каждую быстро набранную букву. Возможна гонка: запрос для слова «сайт» отправлен первым, а его ответ пришёл после ответа для нового слова «дизайн». Экран увеличивает номер поколения загрузки и игнорирует устаревшие результаты. Проверка `mounted` решает другую задачу — экран ещё должен существовать. Та же защита применяется при обновлении списка и догрузке страниц блога.

Такой контроль защищает состояние списка, но не отменяет уже отправленный HTTP-запрос на сервере. Таймаут транспорта тоже ограничивает ожидание, а не гарантирует остановку серверной операции.

## Как отправляется заявка

Форма загружает допустимые услуги и ограничения из `/config`. В ней обязательны имя и контакт; описание и выбор услуг необязательны. Сначала выполняется проверка полей на клиенте. Сервер всё равно проверяет их повторно: интерфейс можно обойти, поэтому клиентская валидация не заменяет серверную.

Учебный пример формата отправки:

```http
POST /api/v1/briefs?lang=ru HTTP/1.1
Host: pip.kz
Content-Type: application/json; charset=utf-8
Accept: application/json
Idempotency-Key: 70d864b3-4ca3-4fb0-859f-59559a3cb686

{
  "name": "Пример клиента",
  "contact": "client@example.com",
  "message": "Нужен сайт компании",
  "services": ["Сайт"]
}
```

Этот пример не отправлялся. Значения `services` нужно брать из актуального `data.brief.serviceOptions`, а не подставлять slug карточки услуги. На сервер уходят только `name`, `contact`, `message`, `services`. В коде формы поле описания называется `description`; адаптер переименовывает его в `message` согласно контракту.

Во время отправки повторное нажатие блокируется. После подтверждённого `201` с `accepted: true` и непустым `id` приложение открывает `BriefSuccessScreen` и показывает номер заявки. При ошибке открытая форма сохраняет введённые значения и предлагает исправить проблему или повторить запрос.

**Идемпотентность** нужна для случая, когда сервер сохранил заявку, а ответ потерялся по пути. Если пользователь повторит запрос с тем же ключом и содержимым, сервер вернёт прежний ID вместо создания дубля. Одна неизменённая форма использует один случайный ключ; изменение содержимого создаёт новый. Сервер помнит ключ 24 часа. Ключ не содержит имени или контакта.

Приложение не выполняет автоматические повторы POST. При `429` кнопка временно блокируется и показывает обратный отсчёт. Ключ и черновик живут в памяти открытой формы: их восстановление после закрытия экрана или перезапуска приложения пока не реализовано. При уходе с заполненной формы появляется подтверждение потери данных. Это ограничивает защиту от дублей после перезапуска и не должно описываться как полноценная офлайн-очередь заявок.

## Ошибки и доступ

Сетевой слой различает отсутствие соединения, таймаут в 15 секунд, HTTP-ошибку и некорректный ответ. Репозиторий преобразует их в сообщения интерфейса, сохраняя код, статус, `requestId` и `Retry-After`, если они пришли от сервера. Например, `404` относится к отсутствующему материалу, `422` — к полям формы, `429` — к ограничению частоты запросов. `requestId` помогает найти конкретный запрос на сервере без записи контактов пользователя в клиентский журнал.

Для публичного каталога и заявки не нужен вход в аккаунт. Это не означает, что административная CMS публична: она существует отдельно, а приложение не получает административных токенов и не может читать чужие заявки через публичный API.

Web-версия дополнительно зависит от CORS — разрешений сервера для origin браузерного приложения. Чтение разрешено с любого origin. Для POST сервер должен доверять точному адресу Web-приложения, включая порт. При проверке локального preview чтение работало, а предварительный запрос отправки получал отказ. Для разрешённой Web-отправки владелец сервера добавляет адрес в `MOBILE_API_ORIGINS`. Нативный клиент не подчиняется браузерному CORS. Подробности и результат проверки находятся в [инструкции по API](api-integration.md#браузер-и-cors).

## Рассказ на 1–2 минуты

> Это клиентское приложение студии Pip на Flutter и Dart. В нём есть услуги, портфолио, блог, контакты и форма заявки. Данные приходят через HTTPS API существующего сайта, поэтому отдельную базу внутри приложения я не создаю.
>
> Код разделён на три слоя. Экраны отвечают за интерфейс и действия пользователя. Репозиторий знает, какие данные нужны экрану, и преобразует ответы в модели Dart. HTTP-клиент отправляет запросы, разбирает JSON и обрабатывает ошибки.
>
> Например, портфолио вызывает метод репозитория. Он отправляет GET на `/projects`. Сервер читает опубликованные проекты из CMS и возвращает JSON. Приложение превращает его в модели и показывает карточки через FutureBuilder. Во время ожидания виден индикатор, при ошибке можно повторить загрузку. Проекты загружаются страницами; старый ответ поиска не может перезаписать новый список.
>
> Форма отправляет POST с именем, контактом, описанием и выбранными услугами. У каждой заявки есть случайный ключ: повтор того же запроса не должен создать дубль. Успех показывается только после подтверждения сервера и получения ID.
>
> Логика проверяется тестами с подставными ответами, а чтение — реальными GET. Реальную заявку при проверке не отправляли. Пока нет офлайн-хранения и восстановления черновика после закрытия приложения. Для браузерной отправки также нужен разрешённый сервером адрес Web-версии.

## Возможные вопросы

**Почему выбран Flutter?** Он позволяет писать интерфейс и логику на Dart для нескольких платформ. В проекте уже есть платформенные каталоги Android, iOS и Web, но их наличие не заменяет отдельную сборку и проверку на устройствах.

**Где хранится информация?** Основной источник — CMS существующего сайта. Приложение получает данные через API и держит открытые экраны в памяти. Постоянной локальной базы и офлайн-кэша здесь нет.

**Зачем нужен репозиторий, если можно вызвать HTTP прямо в кнопке?** Здесь один слой преобразует контракт API в модели для всех экранов. UI проще читать, а сетевой источник можно заменить тестовым без запуска сервера.

**Чем GET отличается от POST в проекте?** GET читает каталог и материалы. POST создаёт заявку. Для POST особенно важны проверка полей, подтверждение успеха и защита повторов ключом.

**Что произойдёт без интернета?** Рабочий режим покажет ошибку и возможность повтора. Демо запускается отдельным параметром и не является автоматически обновляемым офлайн-кэшем.

**Что если ответ сервера потерялся после сохранения заявки?** Повтор неизменённой формы с прежним ключом вернёт её прежний ID в пределах серверного срока хранения ключа. После закрытия формы ключ сейчас не восстанавливается.

**Как проверяется программа?** Транспорт и адаптер проверяются на заранее заданных HTTP-ответах; виджетные тесты проверяют интерфейс с подставным репозиторием. Отдельный сценарий читает рабочий API через GET. Реальный POST в production этими проверками не выполняется.

**Что ещё нужно для публикации?** Проверка нативных сборок на целевых устройствах, релизная подпись, иконки и материалы магазинов. Для полноценного восстановления отправки понадобятся отдельное хранение черновика и ключа, а для Web — согласованный доверенный origin на сервере.
