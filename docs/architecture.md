# Как разобраться в коде Pip

Pip — приложение на Flutter для сайта `pip.kz`. Dart — язык программы, а Flutter — набор средств для создания интерфейса. Экран собирается из виджетов: текста, кнопок, карточек и других элементов.

У приложения уже есть сервер — API сайта. Оно читает через него данные CMS, то есть системы управления материалами студии. Собственной базы данных и административного кабинета в клиенте нет.

## Пять мест, с которых стоит начать

| Место | За что отвечает |
| --- | --- |
| [`lib/main.dart`](../lib/main.dart) | Точка входа: выбирает источник данных и запускает приложение |
| [`lib/app.dart`](../lib/app.dart) | `PipApp`, оформление, меню и переключение вкладок |
| [`lib/screens/`](../lib/screens/) | Отдельный файл для каждого экрана: что показать и что делать при нажатии |
| [`lib/api/`](../lib/api/) | Запросы к сайту, чтение JSON, обработка сетевых ошибок и демо-данные |
| [`lib/models.dart`](../lib/models.dart) | Классы с данными: услуга, проект, статья, заявка, ошибка `AppException` |

Модель — обычный объект с полями. Например, `StudioProject` хранит название, описание и адреса изображений проекта. Она сама ничего не рисует.

Повторяющиеся элементы интерфейса вынесены в `lib/widgets/`: общие состояния загрузки — в `common_widgets.dart`, карточки — в `service_card.dart` и `project_card.dart`. Экраны подключают нужные файлы обычным `import`.

## Как запускается приложение

```text
main → app → экран → ApiService → ApiClient → API сайта
                                              ↕
                                             CMS
```

В `main()` выбирается обычный `ApiService`. Если запуск выполнен с `--dart-define=USE_DEMO_DATA=true`, выбирается `DemoApiService` с локальными примерами. Затем `runApp(PipApp(api: api))` запускает интерфейс.

`PipApp` передаёт этот объект экранам и закрывает его в `dispose`, когда приложение удаляется из дерева виджетов. `ApiService` содержит конкретные методы: `getProjects`, `getService`, `getArticles`, `sendBrief` и другие. `ApiClient` выполняет общую часть: отправляет HTTP-запрос, ждёт ответ и разбирает JSON. Поэтому код этих действий не повторяется на каждом экране.

`DemoApiService` наследует `ApiService`: у него те же методы, но чтение возвращает примеры. Демо включается явно и не отправляет заявки. Ошибка интернета в рабочем режиме не подменяет настоящие данные примерами.

## Как появляется карточка проекта

Для первого знакомства откройте [`portfolio_screen.dart`](../lib/screens/portfolio_screen.dart), затем [`api_service.dart`](../lib/api/api_service.dart).

1. Экран вызывает `getProjects` для первой страницы.
2. `ApiService` выбирает маршрут `projects` и параметры языка, поиска и страницы.
3. `ApiClient` отправляет запрос по HTTPS:

   ```http
   GET /api/v1/projects?lang=ru&page=1&limit=20 HTTP/1.1
   Host: pip.kz
   Accept: application/json
   ```

4. Сервер читает опубликованные проекты из CMS и возвращает JSON — текстовый формат с объектами, массивами и значениями.
5. `ApiClient` проверяет HTTP-статус и читает ответ. `ApiService` превращает данные в объекты `StudioProject`.
6. Экран показывает карточки. Нажатие открывает [`project_screen.dart`](../lib/screens/project_screen.dart), который отдельно вызывает `getProject` для полного текста и галереи.

У ответа API есть `data` — сами записи, и `meta` — сведения об ответе, например номер страницы. Экран работает с готовыми моделями и не разбирает JSON заново.

Приложение рисует свои экраны Flutter. Страницы сайта целиком в WebView не загружаются. Для изображений API возвращает адреса файлов, а Flutter загружает сами изображения отдельно.

## Загрузка и состояние экрана

`Future` означает результат, который появится позже: например, список проектов после ответа сервера. `await` ждёт этот результат, позволяя интерфейсу продолжать обрабатывать действия пользователя. Сам по себе `async` не создаёт отдельный поток.

Общий виджет `AsyncContent` использует `FutureBuilder`: пока запрос выполняется, показывает загрузку; после ответа — данные; при ошибке — сообщение и кнопку повтора. Запрос сохраняется в состоянии экрана, чтобы не запускаться снова при каждом вызове `build`.

`StatelessWidget` подходит элементам без собственного изменяемого состояния. `StatefulWidget` используется там, где нужно хранить, например, текст поиска или выбранные услуги. Вызов `setState` сообщает Flutter, что данные экрана изменились и его нужно перерисовать. Он не сохраняет данные на сервере.

После ожидания проверяется `mounted`: экран мог быть уже закрыт. Контроллеры полей, таймеры и сетевой клиент освобождаются в `dispose`.

Основные вкладки находятся в `IndexedStack` и сохраняют состояние при переключении. Они создаются заранее, поэтому часть запросов может начаться ещё до открытия нужной вкладки. Для обновления данных предусмотрен жест вниз.

## Поиск и следующие страницы

Первая страница — `page: 1`, следующая — `page: 2`. Результат `ContentPage` содержит `items` и `nextPage`. Например, `nextPage == 2` разрешает догрузить вторую страницу, а `nextPage == null` означает конец списка. Уже показанные ID учитываются, чтобы карточки не дублировались.

Пример внутри асинхронной функции:

```dart
// Ждём первую страницу проектов на русском языке.
final result = await api.getProjects(ContentLocale.ru, page: 1);
final projects = result.items; // Полученные проекты.
final nextPage = result.nextPage; // Номер следующей страницы или null.
```

Поиск отправляется через 300 мс после последнего изменения текста. Новый поиск очищает прежние страницы. Каждой загрузке присваивается номер: если старый ответ приходит после нового, экран его игнорирует. Так результаты для старого слова не заменяют актуальные. Это защита интерфейса; сам HTTP-запрос физически не отменяется.

## Как работает форма

Код формы находится в [`brief_screen.dart`](../lib/screens/brief_screen.dart). Она получает разрешённые услуги и ограничения из `/config`. Имя и контакт обязательны, описание и услуги — по желанию. Сначала поля проверяет клиент, затем их независимо проверяет сервер.

Метод `sendBrief` отправляет POST на `/briefs` с четырьмя полями:

```json
{
  "name": "Пример клиента",
  "contact": "client@example.com",
  "message": "Нужен сайт компании",
  "services": ["Сайт"]
}
```

Это учебный пример, он не отправлялся. Значения услуг берутся из `brief.serviceOptions`, а не из адресов карточек каталога. Внутреннее описание заявки преобразуется в поле API `message`.

Перед отправкой создаётся случайный ключ из 32 символов без персональных данных. Он передаётся в заголовке `Idempotency-Key`. Если сервер сохранил заявку, а ответ потерялся, повтор того же содержимого с прежним ключом возвращает прежний ID вместо создания дубля. Сервер помнит ключ 24 часа. Изменение содержимого формы означает новую заявку и новый ключ.

Во время отправки кнопка блокируется. Подтверждение появляется только после `201`, `accepted: true` и полученного ID. При ошибке поля остаются на экране. При `429` форма ждёт указанный сервером срок и показывает обратный отсчёт. Автоматической повторной отправки нет.

`ApiException` описывает сетевую ошибку, а `ApiService` преобразует её в `AppException` с русским сообщением для экрана. В ней также остаются код ошибки и `requestId`, по которому можно найти запрос на сервере.

## Что важно честно сказать на защите

- Данные и заявки хранятся в существующей CMS. Клиент не создаёт собственную базу и не получает административных паролей.
- Рабочий режим требует интернет. Постоянного офлайн-кэша нет.
- Черновик и ключ заявки хранятся только в памяти формы. Перед закрытием заполненной формы есть предупреждение, но после закрытия или перезапуска данные не восстанавливаются.
- Чтение API проверяется GET-запросами. Логика отправки проверяется на подставных ответах, без создания реальных заявок в CMS.
- В браузере чтение работает, а POST требует доверенного адреса Web-приложения в серверной настройке `MOBILE_API_ORIGINS`. При проверке локального адреса предварительный запрос отправки получил отказ. Нативные приложения не ограничиваются браузерным CORS.
- Наличие каталогов Android/iOS и успешная Web-сборка не заменяют проверку на телефоне. Для APK нужны Android SDK и JDK, для iOS — macOS и Xcode; публикация требует релизной подписи и подготовки магазина.

Полные маршруты, ограничения формы и результат проверки CORS описаны в [инструкции по API](api-integration.md).

## Рассказ на 1–2 минуты

> Это приложение студии Pip на Flutter. Его код написан на Dart. Здесь можно посмотреть услуги, проекты, статьи и контакты, а также заполнить заявку. Данные приходят через API существующего сайта из CMS студии.
>
> Разобраться в коде можно по пяти местам. В main начинается работа программы. App задаёт оформление и вкладки. В screens лежат отдельные экраны, в models — классы данных, а в api — запросы к серверу.
>
> Например, экран портфолио вызывает getProjects. ApiService выбирает нужный адрес и параметры, а ApiClient отправляет HTTPS-запрос и читает JSON. Полученные данные превращаются в модели и отображаются карточками. Пока запрос выполняется, виден индикатор загрузки. При ошибке можно повторить попытку. Поиск работает на сервере, проекты загружаются страницами.
>
> Форма отправляет имя, контакт, описание и выбранные услуги. Для повторов используется один случайный ключ: если ответ потерялся, повтор не должен создать вторую заявку. Успех показывается только после подтверждения сервера.
>
> Логика проверяется тестами с подставными ответами, а чтение — настоящими GET-запросами. Реальную заявку при проверке не отправляли. В приложении пока нет офлайн-хранения и восстановления черновика после закрытия. Для отправки из браузера серверу также нужно разрешить адрес Web-версии.

## Короткие ответы на вопросы

**Где находится база данных?** На стороне существующего сайта и CMS. Приложение обращается к API, а не напрямую к базе.

**Зачем два класса для запросов?** `ApiService` знает операции приложения и поля данных. `ApiClient` выполняет одинаковую для всех операций работу с HTTP, JSON и таймаутом.

**Что изменит setState?** Только состояние и отображение экрана. Для сохранения заявки нужен отдельный POST.

**Почему данные не появляются сразу?** Запрос к серверу занимает время. `Future` представляет будущий результат, а `FutureBuilder` показывает нужное состояние загрузки.

**Как проверить приложение без сервера?** Тесты подставляют ответы HTTP или тестовый `ApiService`. Для просмотра интерфейса можно явно включить `DemoApiService`.
