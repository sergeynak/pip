# Как разобраться в макете Pip

**Сверстан интерфейс, настроены переходы и локальные данные; подготовлены модели и методы для подключения API.** Это точное описание текущей работы для защиты: настоящего обмена с сервером пока нет.

Flutter помогает создавать интерфейс из виджетов — текста, кнопок, карточек и экранов. Dart — язык, на котором написана программа.

## Пять мест в проекте

| Место | Что там читать |
| --- | --- |
| [`lib/main.dart`](../lib/main.dart) | Начало программы: создаётся `DemoApiService` и запускается `PipApp` |
| [`lib/app.dart`](../lib/app.dart) | Общая тема, меню и вкладки приложения |
| [`lib/screens/`](../lib/screens/) | Что показывает каждый экран и куда ведут нажатия |
| [`lib/api/`](../lib/api/) | Локальные примеры, заготовки методов и подготовленный сетевой клиент |
| [`lib/models.dart`](../lib/models.dart) | Объекты с данными: например, название и описание проекта |

Повторяющиеся элементы вынесены в `lib/widgets/`. Например, `common_widgets.dart` содержит общие состояния интерфейса, а `project_card.dart` — карточку проекта. Файлы подключаются обычным `import`.

## Как всё работает сейчас

```text
main → PipApp → экран → DemoApiService → локальные модели → виджеты
```

Откройте [`portfolio_screen.dart`](../lib/screens/portfolio_screen.dart). Экран вызывает `getProjects`, но объект `DemoApiService` берёт записи из списка в [`demo_api_service.dart`](../lib/api/demo_api_service.dart). Затем карточки показывают поля моделей `StudioProject`.

При нажатии на карточку открывается [`project_screen.dart`](../lib/screens/project_screen.dart). Он получает подробности того же локального примера. Услуги и статьи устроены аналогично. Цены помечены как примеры, образцы контактов не открывают ссылки. Настоящие данные и изображения из CMS пока не загружаются.

Поиск сравнивает введённый текст с названием и категорией локальных проектов. Пауза в 300 мс после ввода сохранена для будущих сетевых запросов. Номер загрузки защищает экран от устаревшего результата, но сейчас сервер в поиске не участвует.

## Что означают Future и setState

Методы возвращают `Future` — результат, который может появиться позже. Сейчас демо-данные доступны сразу, но такая форма методов позволит подключить сеть, не переделывая каждый экран.

`AsyncContent` использует `FutureBuilder`: он умеет показать загрузку, данные или ошибку. Это подготовленные состояния интерфейса, а не доказательство обращения к серверу.

`StatefulWidget` нужен там, где есть изменяемые данные: текст поиска, выбранная вкладка или поля формы. `setState` сообщает Flutter, что экран нужно обновить. `StatelessWidget` описывает элементы без собственного изменяемого состояния.

После ожидания проверяется `mounted`: экран мог быть уже закрыт. В `dispose` освобождаются контроллеры и таймеры. Эти проверки сохраняют правильное поведение при будущей асинхронной загрузке.

## Что происходит с заявкой

[`brief_screen.dart`](../lib/screens/brief_screen.dart) проверяет поля и собирает объект `BriefDraft`. При нажатии кнопки вызывается `sendBrief`. Демо-метод сообщает, что API ещё не подключён и заявка не отправлена. Введённый текст остаётся на открытом экране.

Экран успешной отправки свёрстан отдельно для будущего подтверждения сервера. Сейчас форма остаётся открытой и показывает сообщение об отсутствии подключения. Черновик хранится только в памяти: после закрытия формы или приложения он не восстанавливается.

Для дальнейшего подключения подготовлены ключ защиты от повторных заявок и обработка ограничения частоты отправки. Пока настоящие POST-запросы не выполняются, это подготовленная логика, а не работающая отправка.

## Что потребуется добавить позже

В [`api_service.dart`](../lib/api/api_service.dart) есть методы `getServices`, `getProjects`, `getArticles`, `sendBrief` и другие. В них стоят `TODO`, а вызов сообщает `API_NOT_CONNECTED`.

Будущая цепочка будет такой:

```text
экран → ApiService → ApiClient → API сайта → CMS
```

`ApiClient` уже умеет отправлять HTTP-запросы, разбирать JSON и обрабатывать сетевые ошибки. Нужно использовать его внутри заготовок, преобразовать ответы в модели и затем заменить демо-объект в `main`. Изменение одного адреса API этого не делает.

Модель `ContentPage` и параметр `page` подготовлены для страниц результатов. Сейчас примеры возвращают `nextPage: null`: догружать нечего. В галерее показаны две локальные декоративные иллюстрации. Для настоящих изображений понадобится подключение данных сайта.

## Короткий рассказ для защиты

> В проекте сверстан интерфейс приложения Pip на Flutter. Настроены вкладки, переходы к подробным страницам и форма с проверкой полей. Наполнение пока локальное: услуги, проекты и статьи находятся в демонстрационном сервисе. Поиск фильтрует эти примеры.
>
> Код разделён на запуск, приложение, экраны, работу с данными и модели. Методы для API и сетевой клиент подготовлены, но настоящие запросы ещё не подключены. Форма показывает сообщение, что заявка не отправлена. Следующий этап — реализовать методы получения данных и отправки по контракту сайта.

**Где база данных?** В этой версии клиент своей базы не имеет; он показывает локальные списки. В будущем основным источником станет существующая CMS сайта.

**Что уже готово для API?** Модели данных, методы-заготовки, сетевой клиент, настройка адреса и состояния экранов.

**Что ещё предстоит сделать?** Подключить данные сайта и отправку заявок, затем проверить сборку на телефоне.

Технические шаги будущего подключения описаны в [инструкции по API](api-integration.md).
