# Подготовка к подключению API

Сейчас приложение показывает локальные примеры через `DemoApiService`. API сайта не вызывается, а заявки не отправляются. Адрес `https://pip.kz/api/v1` известен для будущего подключения: [документация сервера](https://pip.kz/api/docs), [контракт OpenAPI](https://pip.kz/api/v1/openapi.json).

## Что подготовлено

- `lib/models.dart` — классы для услуг, проектов, статей, контактов, формы и ошибок.
- `lib/api/api_service.dart` — методы с `TODO`, которые пока возвращают `AppException` с кодом `API_NOT_CONNECTED`.
- `lib/api/api_client.dart` — HTTP, JSON, таймаут и сетевые ошибки. Макет этот клиент не вызывает.
- `lib/api/api_config.dart` — настройка адреса; значение по умолчанию пустое.
- `lib/screens/` — состояния загрузки, данных, ошибки и переходы между экранами.

`main.dart` всегда создаёт `DemoApiService`. Одного заполнения адреса недостаточно, чтобы включить реальную загрузку.

## Настройка адреса

Сейчас `config/development.example.json` содержит:

```json
{
  "API_BASE_URL": ""
}
```

При будущем подключении можно создать `config/development.local.json` с нужным HTTPS-адресом и передать его при запуске:

```sh
flutter run --dart-define-from-file=config/development.local.json
```

Файлы `*.local.json` исключены из Git. Значения `--dart-define` попадают в сборку: пароли и административные ключи там хранить нельзя. Публичные методы указанного API не требуют таких секретов.

## Планируемое соответствие методов и маршрутов

Эта таблица описывает будущую реализацию, а не текущие запросы приложения. Все пути дополняются адресом `https://pip.kz/api/v1`.

| Метод приложения | Маршрут сервера |
| --- | --- |
| `getContacts`, `getBriefOptions` | `GET /config` |
| `getServices`, `getService` | `GET /services`, `GET /services/{slug}` |
| `getProjects`, `getProject` | `GET /projects`, `GET /projects/{slug}` |
| `getArticles`, `getArticle` | `GET /posts`, `GET /posts/{slug}` |
| `sendBrief` | `POST /briefs` |

Сервер возвращает JSON с `data` и `meta`. При подключении нужно проверить поля и преобразовать их в модели. Полный текст и галерея запрашиваются по `slug` карточки. Для списков подготовлены числовой параметр `page` и поле `ContentPage.nextPage`; сейчас демо-данные не требуют следующих страниц. Поиск пока выполняется локально, позже его можно передавать серверу параметром `q`.

## Будущая отправка формы

По контракту сервера заявка содержит только следующие поля:

```json
{
  "name": "Пример клиента",
  "contact": "client@example.com",
  "message": "Нужен сайт компании",
  "services": ["Сайт"]
}
```

Это пример формата, он не отправляется макетом. Варианты услуг нужно будет брать из `/config`, а `BriefDraft.description` преобразовывать в `message`. `BriefDraft.services` хранит названия выбранных вариантов.

При реализации отправки нужно сохранить подготовленную защиту повторов: одна неизменённая заявка использует прежний случайный ключ в `Idempotency-Key`. Сервер хранит его 24 часа. Подтверждение допускается только после `201`, `accepted: true` и полученного ID. При `429` нужно выдержать `Retry-After`; автоматически повторять POST не следует. Ключ и черновик сейчас существуют только в памяти открытой формы.

## Что сделать для подключения

1. Реализовать `TODO` в `ApiService` через `ApiClient` и преобразование JSON в модели.
2. Проверить методы на подставных ответах, затем отдельно проверить чтение API.
3. Указать адрес и заменить `DemoApiService` в `main` на готовый `ApiService`.
4. Отдельно проверить отправку в согласованном окружении и работу на целевых устройствах.

Проверки транспорта с подставными ответами не означают, что приложение уже подключено к рабочему серверу. Сценария живой проверки в текущем макете нет.

## Браузер и ограничения

При будущем подключении чтение API разрешено с любого браузерного origin. Для POST владелец сервера должен разрешить точный адрес Web-приложения в `MOBILE_API_ORIGINS`, включая схему, хост и порт. Изменение `API_BASE_URL` не меняет это разрешение. Отключать CORS не требуется. Нативные Android/iOS-приложения не ограничиваются браузерным CORS.

Сейчас эти разрешения не влияют на локальный просмотр: макет не отправляет запросы к API. У него нет собственной базы, авторизации, постоянного офлайн-кэша или сохранения черновика после закрытия. Нативные сборки и публикация в магазинах потребуют отдельной проверки и настройки.
