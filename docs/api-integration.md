# Интеграция с API Pip

Рабочий адрес — `https://pip.kz/api/v1`. Контракт сервера: [документация](https://pip.kz/api/docs) и [OpenAPI](https://pip.kz/api/v1/openapi.json). Публичные методы не требуют авторизации, cookies или API-ключа.

`lib/main.dart` выбирает `ApiService` для работы с сайтом или `DemoApiService` для локальных примеров и передаёт объект в `PipApp(api: api)`. `lib/app.dart` передаёт его экранам и закрывает клиент в `dispose`. Рабочий режим используется по умолчанию; `USE_DEMO_DATA=true` явно включает демо. Сетевая ошибка не переключает приложение на примеры.

Основной код находится в `lib/api/api_service.dart`: конкретные методы `getProjects`, `getService`, `sendBrief` и другие. Рядом находится `ApiClient`, который отправляет HTTP-запросы и разбирает JSON. Модели данных и ошибка `AppException` описаны в `lib/models.dart`. `DemoApiService` наследует `ApiService` и заменяет получение данных локальными примерами.

## Настройка

По умолчанию `API_BASE_URL` равен `https://pip.kz/api/v1`:

```sh
flutter run -d chrome --web-port=5173
flutter run --dart-define=API_BASE_URL=https://example.com/api/v1
flutter run --dart-define=USE_DEMO_DATA=true
```

Можно использовать файл конфигурации:

```sh
flutter run --dart-define-from-file=config/development.local.json
```

```json
{
  "API_BASE_URL": "https://pip.kz/api/v1"
}
```

Файлы `*.local.json` исключены из Git. `--dart-define` встраивает значения в сборку, поэтому не подходит для секретов. Адрес должен быть HTTPS без логина, пароля, query и fragment. Для разработки `ApiConfig` также разрешает HTTP только для `localhost`, `127.0.0.1`, `::1` и Android-адреса хоста `10.0.2.2`. Произвольный LAN-адрес по HTTP текущей конфигурацией не разрешён. Разрешения незашифрованного трафика Android/iOS настраиваются отдельно; для рабочего API это не требуется.

## Маршруты

Все пути в таблице дополняются базовым адресом `/api/v1`.

| Метод и путь | Метод `ApiService` | Использование |
| --- | --- | --- |
| `GET /config?lang=ru` | `getContacts`, `getBriefOptions` | Контакты и допустимые значения формы |
| `GET /services?lang=ru` | `getServices` | Каталог услуг |
| `GET /services/{slug}?lang=ru` | `getService` | Описание, состав работ, FAQ и связанные материалы |
| `GET /projects?lang=ru&page=1&limit=20` | `getProjects` | Список проектов, поиск `q`, фильтр `featured` |
| `GET /projects/{slug}?lang=ru` | `getProject` | Полный текст и галерея проекта |
| `GET /posts?lang=ru&page=1&limit=20` | `getArticles` | Список статей |
| `GET /posts/{slug}?lang=ru` | `getArticle` | Полный текст статьи |
| `POST /briefs?lang=ru` | `sendBrief` | Сохранение заявки в CMS |

В маршруты деталей передаётся `slug` из ответа списка, закодированный как сегмент URL. Внутренний ID записи и её slug могут различаться. `GET /openapi.json` служит документацией: у него нет обёртки `data`, поэтому он не используется как обычный метод `ApiClient`.

## Ответы и преобразование данных

Обычный успешный ответ имеет обёртку:

```json
{
  "data": [],
  "meta": {
    "requestId": "example-request-id",
    "lang": "ru",
    "pagination": {
      "page": 1,
      "limit": 20,
      "total": 0,
      "totalPages": 0,
      "hasNext": false,
      "hasPrevious": false
    }
  }
}
```

`ApiClient` разбирает UTF-8 JSON, HTTP-статус и `meta` в `ApiResponse`, `ApiMeta`, `PageInfo`. `ApiService` проверяет поля и создаёт модели `StudioService`, `StudioProject`, `StudioArticle`, `StudioContact`, `BriefOptions` и `BriefReceipt`. Экран получает готовые объекты: например, читает `project.title`, а не разбирает JSON самостоятельно. Дополнительные неизвестные поля ответа не мешают чтению известных полей.

| Ответ API | Преобразование в приложении |
| --- | --- |
| Услуга | `slug` становится `StudioService.id`; `summary` списка или `lead` деталей — описанием; `sections`, `faq`, связанные `projects` сохраняются отдельно |
| Проект | Числовой `id` становится строковым ID модели; `slug` сохраняется отдельно; `excerpt` списка заменяется полным `content` при открытии деталей |
| Галерея | Сохраняются URL оригинала и миниатюры, подпись, `kind`, ширина и высота; обложка хранится отдельно |
| Статья | `excerpt` или `content` разделяется на абзацы по пустым строкам; одиночные переводы строк сохраняются; сохраняются автор, дата и URL |
| `config.studio` | Email, Telegram, сайт и сведения о студии преобразуются в `StudioContact` |
| `config.brief` | `serviceOptions`, `limits` и `idempotencyTtlSeconds` преобразуются в `BriefOptions` |

Для проектов и статей `ApiService` проверяет `contentFormat: "plain_text"`. Неожиданный тип обязательного поля или неподдерживаемый формат приводит к понятной ошибке ответа.

- У услуги начальная цена берётся из `price.label`; `amountFrom: null` означает индивидуальный расчёт. Цена не генерируется приложением.
- Списки проектов и статей содержат анонс. Полный `content` и галерею необходимо догружать маршрутом деталей.
- `content` — обычный текст; клиент не исполняет его как HTML и не использует WebView для этих экранов.
- Ссылки на обложки, галерею и страницы сайта абсолютные. Базовый адрес API к ним не добавляется.
- `publishedAt` — дата ISO 8601; перед показом дата переводится в местное время.
- `fieldLanguages` сохраняет фактический язык полей. API поддерживает `ru`, `en`, `kk`; `kz` — серверный псевдоним `kk`. Интерфейс приложения пока русский, переключателя языка нет. Услуги и настройки могут оставаться русскими при другом `lang`.

## Поиск и страницы

API использует номера страниц. `page` начинается с 1, `limit` допускает 1–50; запрос клиента использует 20 элементов. `q` — подстрока до 100 символов в названии, анонсе или категории. Поиск выполняется сервером.

`getProjects` и `getArticles` принимают целое число `page`, по умолчанию 1. Ответ приложения — `ContentPage` с записями `items` и номером следующей страницы `nextPage`. Если API сообщает `hasNext: true`, `nextPage` равен текущей странице плюс один; иначе он равен `null`. При новом поиске экран очищает список и начинает со страницы 1. Уже показанные ID учитываются при добавлении следующей страницы, чтобы не дублировать карточки.

Поиск отправляется через 300 мс после последнего изменения текста; поле ограничено 100 символами. Экран отслеживает поколение загрузки: запоздалый ответ старого поиска или старой страницы не меняет новый список. Блог применяет такую же защиту при обновлении и догрузке. Это защита состояния интерфейса, а не физическая отмена HTTP-запроса. Сам транспорт не предоставляет операции отмены запроса. Основные вкладки и детали поддерживают повторную загрузку жестом вниз.

## Заявка

Значения услуг берутся именно из `GET /config → data.brief.serviceOptions`. Это разрешённые строки для формы, а не slug услуг из каталога.

В JSON отправляются только четыре поля:

```json
{
  "name": "Пример клиента",
  "contact": "client@example.com",
  "message": "Нужен сайт компании",
  "services": ["Сайт"]
}
```

Это пример формата, не отправленный запрос. Значение `Сайт` подходит только если присутствует в актуальном `serviceOptions`. `BriefDraft.description` преобразуется в поле API `message`, а `BriefDraft.services` содержит выбранные названия услуг для `services`.

Заголовки: `Content-Type: application/json; charset=utf-8`, `Accept: application/json`, `Idempotency-Key: <ключ операции>`. Язык передаётся параметром `lang`, а не лишним полем тела.

| Поле | Ограничение сервера |
| --- | --- |
| `name` | Обязательное, 2–100 символов |
| `contact` | Обязательное, 3–200 символов |
| `message` | Необязательное, до 5000 символов |
| `services` | Необязательное, максимум 6 допустимых строк |

JSON ограничен 32 КБ. Неизвестные поля отклоняются. Клиент подтверждает успех только при `201` и `data: {"accepted": true, "id": "..."}`; одного отсутствия сетевой ошибки недостаточно.

Ключ защиты от повторного создания заявки создаётся в форме перед отправкой. Это случайный ключ из 32 символов без персональных данных. Повтор неизменённой формы использует тот же ключ; изменение содержимого создаёт новый. На время отправки кнопка блокируется. Сервер хранит соответствие ключа заявке 24 часа: прежние ключ и содержимое возвращают прежний ID, другое содержимое с прежним ключом — `409 IDEMPOTENCY_CONFLICT`.

После таймаута сервер уже мог сохранить заявку. Поэтому повтор с прежним ключом защищает от дубля. Автоматических повторов POST нет. Черновик и ключ хранятся только в памяти открытой формы; закрытие экрана или приложения не обеспечивает восстановление этой операции. Публичного API чтения заявок нет — их видит студия в своей CMS.

При уходе с заполненной формы приложение просит подтвердить потерю черновика. Это защита от случайного закрытия, не постоянное хранение. Переход из карточки услуги заполняет описание её названием; slug услуги автоматически не превращается в значение `services`.

## Ошибки

Таймаут — 15 секунд. Он завершает ожидание клиента, но сам по себе не доказывает, что сервер прекратил обработку. Различаются сетевая ошибка, таймаут, HTTP-ошибка и некорректный ответ. `ApiClient` создаёт `ApiException`; `ApiService` превращает её в `AppException` с русским сообщением для экрана. Сырой HTML от прокси не показывается пользователю.

| Ситуация | Поведение |
| --- | --- |
| Нет сети или истёк таймаут | Сообщение об ошибке и ручной повтор; поля формы остаются на экране |
| `400`, `413`, `415`, `422` | Исправить параметры, размер или поля; автоматический повтор не исправит запрос |
| `403 ORIGIN_NOT_ALLOWED` | Проверить разрешённый origin Web-сборки |
| `404 NOT_FOUND` | Материал удалён или недоступен; показать ошибку деталей |
| `409 IDEMPOTENCY_CONFLICT` | Ключ не соответствует содержимому заявки |
| `429 RATE_LIMITED` | Форма блокирует повторную отправку и показывает обратный отсчёт по `Retry-After`; без корректного заголовка используется 60 секунд |
| `500`, `503` | Повторить позже; для той же заявки сохранить ключ и тело |

`requestId` берётся из `meta.requestId` или `X-Request-ID` и помогает сопоставить ошибку с серверным журналом. Код хранит HTTP-статус и `error.code`, чтобы логика не зависела от текста сообщения. В запросы чтения и отправки не добавляются административные токены; контактные данные не нужны для диагностики сетевого слоя.

## Браузер и CORS

Публичные GET разрешены с любого origin. POST из браузера разрешён только с доверенных origin. Дополнительный адрес Web-приложения настраивается **на сервере** в `MOBILE_API_ORIGINS`, например `https://app.example.com,http://localhost:5173`; изменение применяется после перезапуска серверного процесса.

Origin включает схему, хост и порт. `http://localhost:5173` и `http://127.0.0.1:5173` — разные origin. Поэтому фиксированный `--web-port=5173` удобен для согласованной локальной проверки. Пока origin не разрешён, каталог в браузере может загружаться, а отправка формы — завершаться отказом или сетевой ошибкой браузера. Это не решается параметром `API_BASE_URL` или заголовком в Flutter-клиенте.

При проверке 20 октября 2026 года `GET /config` с `Origin: http://127.0.0.1:8765` вернул `200` и `Access-Control-Allow-Origin: *`. Предварительный запрос `OPTIONS /briefs` с тем же origin вернул `403 ORIGIN_NOT_ALLOWED` без разрешающего заголовка. Сам POST не отправлялся. Это проверка существующей настройки, а не изменение серверного списка доверенных адресов.

Нативные Android/iOS-приложения не ограничиваются браузерным CORS и не должны вручную добавлять `Origin`. Cookies для этих публичных методов не используются. Разрешать произвольную отправку со всех сайтов или отключать CORS для работы клиента не требуется.

## Границы проверки

Для чтения рабочего API предусмотрена команда `dart run tool/check_api.dart`: настройки, услуги и детали, проекты и следующая страница, избранные проекты, статьи и детали. Сценарий выполняет только GET. Отправка формы проверяется подставным HTTP-клиентом и тестовым `ApiService`, без создания реальных заявок в CMS. Такая проверка тела, заголовков, ошибок и подтверждения не равна проверке реальной отправки с конкретного браузерного адреса или устройства.

Приложение не реализует собственную базу, авторизацию, офлайн-кэш или постоянное хранение черновиков. Ответы API имеют `Cache-Control: no-store`; данные открытых экранов остаются в оперативной памяти до обновления или пересоздания экрана.
